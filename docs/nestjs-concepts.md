# NestJS Concepts, Techniques & Design — Notes

Working notes on how this codebase is built and *why*. Written against the
actual files, so every claim is checkable. If you know Laravel, the comparisons
throughout should shorten the ramp.

---

## 1. The mental model

The single most useful thing to internalise: **Nest is not a framework that
calls your code — it is a container that assembles your code, then gets out of
the way.**

Laravel gives you a service container plus a large amount of convention
(facades, `Mail::`, `Auth::`, `php artisan make:*`). Nest gives you a container
and almost no convention. There is no `Auth` facade, no mail component, no
queue. You wire those yourself from libraries — which is why this project has
`nodemailer`, `passport-jwt`, `bcrypt`, and `zod` as direct dependencies rather
than framework features.

The trade: more assembly up front, but every piece is replaceable and explicit.
Nothing in this codebase happens by magic string lookup.

### Three primitives everything is built from

| Primitive | What it is | Laravel analogue |
|---|---|---|
| **Provider** | Any class the container can construct and inject | Service container binding |
| **Module** | A scope that declares what it provides and what it exports | Service provider |
| **Decorator** | Metadata attached to a class/method, read later by the framework | Attributes / middleware annotations |

That is genuinely most of it. Guards, interceptors, pipes, filters, strategies,
services, repositories — all are providers with a particular interface.

## 2. Dependency injection — how it actually works

```ts
@Injectable()
export class UsersService {
  constructor(private readonly userRepository: UserRepository) {}
}
```

No binding, no registration by name. Nest reads the **constructor parameter
type** and finds the provider whose class matches.

This only works because of two `tsconfig.json` settings:

- `emitDecoratorMetadata: true` — makes TypeScript emit the parameter types
  into the compiled JS as metadata. Without it the types are erased and Nest
  sees nothing.
- `reflect-metadata` imported at startup — the runtime library that reads them.

**Remove either and DI breaks at runtime, not compile time.** The class
constructs with `undefined` for every dependency and you get a null-reference
error deep in a request. This is the single most confusing Nest failure mode, so
it is worth knowing the cause.

### When the type isn't enough

Sometimes there is no class to point at — a config object, for example. Then you
need an explicit token:

```ts
constructor(
  @Inject(jwtConfig.KEY)
  private readonly config: ConfigType<typeof jwtConfig>,
) {}
```

`jwtConfig.KEY` is a string token generated by `registerAs`. `ConfigType<typeof
jwtConfig>` derives the shape from the factory's return type, so the config
object stays fully typed with no interface duplication.

### Providers are singletons

One instance per application, constructed once at boot. This is why
`MailerService` builds its SMTP connection pool in the constructor — that code
runs exactly once, not per request. It is also why you must not store
request-specific state on a provider: every request shares the same object.

## 3. Modules — the dependency graph

```ts
@Module({
  imports: [TypeOrmModule.forFeature([User])],  // what I need
  controllers: [UsersController],                // my routes
  providers: [UsersService, UserRepository],     // what I construct
  exports: [UsersService],                       // what others may use
})
export class UsersModule {}
```

The rule that matters: **`providers` is private, `exports` is public.**
`UsersModule` provides both `UsersService` and `UserRepository` but exports only
the service. So `AuthModule` can inject `UsersService` (it imports
`UsersModule`) but *cannot* inject `UserRepository` — the container will refuse.

That is not bureaucracy. It is what enforces the layering rule below: auth code
physically cannot reach into the users table directly. It must go through the
service.

### `@Global()` — use sparingly

`CommonModule` is marked `@Global()`, so its providers are available everywhere
without importing it. That is correct for genuinely app-wide cross-cutting
concerns and wrong for almost everything else. Two global modules here:
`CommonModule` and `ConfigModule` (via `isGlobal: true`). Feature modules are
never global.

### Async module configuration

```ts
TypeOrmModule.forRootAsync({
  inject: [databaseConfig.KEY],
  useFactory: (config: ConfigType<typeof databaseConfig>) => ({ ... }),
})
```

`forRoot` takes a static object. `forRootAsync` takes a factory that runs after
DI is available — which is how the database module reads validated config rather
than poking at `process.env` directly. Same pattern in `CommonModule` for the
throttler.

Convention worth knowing: `forRoot`/`forRootAsync` configures a module once,
app-wide. `forFeature` registers scoped pieces per module — here, which entities
a feature's repositories may inject.

## 4. The five-layer architecture

```
src/
├── common/    cross-cutting behaviour, wired once via CommonModule
├── config/    one typed factory per concern + config.module.ts
├── database/  migrations, seeders, subscribers
├── api/       every route — a folder per version, a folder per feature
└── shared/    base classes + infrastructure modules
```

### Why the leaves of `common/` stay Nest-free

`common/` as a whole depends on NestJS — it holds guards, interceptors, pipes
and filters. But its leaf folders (`types/`, `enums/`, `utils/`,
`constants/`) deliberately do not import anything from Nest.

That is what keeps them safe to import from *anywhere* without
circular-dependency risk. The moment a leaf imports a Nest module you have a
potential cycle: feature → common → module → feature. Keeping the leaves pure
means the import graph stays a tree from those files down.

### Why the cross-cutting layer exists

Behaviour that applies to every request lives in `common/` once, so features
never reimplement it. Concretely: a controller in this codebase does **not** shape its
own response envelope (the interceptor does it), does **not** sanitise its own
input (the pipe does it), and does **not** format its own errors (the filter
does it).

### The separation rule

- **Controllers**: routing, guards, decorators. No business logic.
- **Services**: business logic. No SQL.
- **Repositories**: all database queries. No business rules.

`UsersController.me()` is the model — it takes an id from the token, calls the
service, maps to a response DTO. Three lines, no decisions.

The test for whether you got this right: **deleting a feature should be
`rm -rf` on its folder plus one line out of `AppModule`.**

### Why repositories wrap the ORM

`UserRepository` injects TypeORM's `Repository<User>` and exposes named methods
(`findByEmailWithPassword`, `existsByEmailOrPhone`). It would be less code to
inject `Repository<User>` into the service directly.

Three reasons not to:

1. **Every query is findable.** All user SQL is in one file. "Where do we query
   users by phone?" has a grep-able answer.
2. **Injection risk is contained** to one auditable file (A03).
3. **Services become testable** without a database — mock the repository.

## 5. Decorators and the metadata pattern

This is the technique that makes Nest feel magical until you see the mechanism,
at which point it becomes obvious. It has exactly three parts.

**Part 1 — a decorator writes metadata:**

```ts
export const IS_PUBLIC_KEY = 'is_public';
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);
```

**Part 2 — you tag a handler:**

```ts
@Public()
@Post('login')
login(...) {}
```

**Part 3 — a guard reads it back:**

```ts
const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
  context.getHandler(),   // method-level first
  context.getClass(),     // then controller-level
]);
```

`getAllAndOverride` checks the targets in order and takes the first hit, so a
method-level tag overrides a controller-level one. That ordering is the whole
point — it lets you set a default on the controller and exempt one route.

Four decorators here follow this pattern: `@Public()`, `@Roles()`,
`@ResponseMessage()`, and `@CurrentUser()` (a param decorator, which reads the
request instead of metadata).

### The deny-by-default design

`JwtAuthGuard` is registered as a global `APP_GUARD`. Every route requires a
valid token unless it opts out with `@Public()`.

Compare the two possible designs:

- **Opt-in protection** (`@UseGuards(JwtAuthGuard)` per route): forgetting the
  decorator silently exposes an endpoint.
- **Opt-out protection** (this design): forgetting `@Public()` breaks the
  endpoint loudly in testing.

The second fails closed. That is the entire argument, and it is why the auth
routes each carry an explicit `@Public()` (A01).

## 6. The request lifecycle — order matters

This is the highest-value thing to memorise, because misplacing logic here
causes bugs that look inexplicable.

```
Request
  │
  ├─ Middleware
  ├─ Guards ─────────────────► can reject (401/403/429)
  ├─ Interceptors (pre)
  ├─ Pipes ──────────────────► validate & transform body
  ├─ ► HANDLER ◄
  ├─ Interceptors (post) ────► reverse order
  └─ Exception filter ───────► catches anything thrown above
Response
```

### Guards run in registration order

From `core.module.ts`:

```ts
{ provide: APP_GUARD, useClass: ThrottleGuard },  // 1
{ provide: APP_GUARD, useClass: JwtAuthGuard },   // 2
{ provide: APP_GUARD, useClass: RolesGuard },     // 3
```

Throttle first, and that ordering is deliberate: rate limiting must fire
*before* authentication, or an attacker gets unlimited credential-stuffing
attempts as long as each one fails auth. Cheapest check first also means less
work spent on requests that get rejected.

Then authentication (who are you), then authorization (may you). Roles cannot
run before JWT — it reads `request.user`, which the JWT strategy attaches.

### Guards run BEFORE pipes

Non-obvious and it bites people. `ThrottleGuard.getTracker()` reads
`req.body.email` — but that body has **not** been validated yet. So it defends
itself:

```ts
const email = typeof body?.email === 'string' ? body.email.toLowerCase().trim() : '';
```

Never assume a validated body inside a guard. It has not happened yet.

### Interceptors are onion-shaped

Registered `[Logging, Timeout, Transform]`. On the way in they run in that
order; on the way out, **reverse** — Transform first (innermost), then Timeout,
then Logging.

That is why the logging interceptor's timing measurement includes everything
inside it, and why Transform can set the envelope before Logging observes the
final status.

### Errors skip the interceptors

When a handler throws, the response path does not run — `AllExceptionsFilter`
writes the response itself. That is why the filter manually constructs
`{ data, message, status }`: it has to reproduce the envelope, because
`ResponseInterceptor` never sees an error. Change the envelope shape in one
place and you must change the other.

## 7. Validation — the Zod pipe

Nest's documented default is `class-validator` + `class-transformer`, driven by
decorators on DTO classes. This project uses Zod instead.

The reason is that Zod schemas are **values, not classes**, so they compose:

```ts
export const passwordSchema = z.string().min(8).max(72)
  .regex(/[a-z]/).regex(/[A-Z]/).regex(/\d/);
```

One definition, reused by `register.dto.ts` and `reset-password.dto.ts`. And the
DTO *type* is derived, never written twice:

```ts
export type RegisterDto = z.infer<typeof registerSchema>;
```

The schema is the single source of truth for both runtime validation and the
compile-time type. They cannot drift.

### The security property

Zod objects are **non-strict by default**: unknown keys are *stripped*, not
rejected. So a client posting

```json
{ "email": "...", "password": "...", "role": "admin" }
```

gets a parsed object with no `role` key at all. Mass assignment is structurally
impossible (A01) — there is a test asserting exactly this in
`register.dto.spec.ts`.

Note the pipe returns `result.data` (the *parsed* value), not the input. That is
what makes stripping and coercion effective. Returning the original would
validate but not sanitise.

### Cross-field rules

```ts
.refine((data) => data.password === data.password_confirmation, {
  path: ['password_confirmation'],
  message: 'password_confirmation must match password',
})
```

`path` is what makes the error point at the right field for a form UI.

### Pipe placement

```ts
register(@Body(new ZodValidationPipe(registerSchema)) dto: RegisterDto)
```

Attached to the `@Body()` parameter, **not** via `@UsePipes()`. With `@UsePipes`
the pipe runs against *every* handler argument — including `@Req()` — and the
schema would reject the raw request object. Parameter-scoped is correct here.

## 8. Authentication technique

### Passport strategies as providers

```ts
export class JwtStrategy extends PassportStrategy(Strategy, 'jwt') {
```

`PassportStrategy()` is a mixin returning a base class; `'jwt'` names the
strategy so `AuthGuard('jwt')` can find it. `super()` in the constructor
configures extraction and verification; `validate()` receives the decoded
payload and whatever it returns becomes `request.user`.

Two strategies here, deliberately distinct: `'jwt'` (access, from the
`Authorization` header) and `'jwt-refresh'` (refresh, from the request body).

### Signature validity is not enough

The critical design decision, in `JwtStrategy.validate()`: after the signature
verifies, the user is **re-read from the database** on every request.

A JWT is a snapshot. If you trust the payload alone, a role demotion or an
account ban does not take effect until the token expires. Re-reading costs one
indexed primary-key lookup and makes revocation immediate (A01).

Then two further checks:

- `payload.type !== TokenType.Access` → reject. Every token carries a `type`
  claim, so a refresh token cannot be replayed at an access-token endpoint.
- `assertNotStale(payload, user)` → reject tokens issued at or before
  `credentialsChangedAt`.

### Three secrets, not one

`jwt.config.ts` holds separate secrets for access / refresh / reset, and
`JwtModule.register({})` deliberately registers **no** default secret — every
sign and verify call passes its own key explicitly.

The effect: token-type confusion fails at the *signature*, not at a payload
check. A reset token presented as an access token cannot even be parsed. Defence
in depth on top of the `type` claim.

### `credentialsChangedAt` — revocation without a denylist

This is the most elegant idea in the module. Rather than a table of revoked
tokens, one timestamp column on `users`. Any token whose `iat` is at or before
it stops verifying.

One column write invalidates every access token, every refresh token, and the
spent reset token simultaneously. `TokenService.assertNotStale` is the only
place it is enforced, called from both strategies and from `resetPassword`.

### Refresh rotation and family revocation

`TokenService.rotate()` revokes the presented session and issues a new one, so a
refresh token is usable exactly once. `resolveSession()` handles the interesting
case:

```ts
if (session.tokenHash !== hashToken(presentedToken)) {
  await this.refreshTokenRepository.revokeAllForUser(session.userId);
  throw new UnauthorizedException('Session expired or revoked');
}
```

The session exists but holds a *different* token — meaning someone replayed a
pre-rotation token. Either the legitimate user or an attacker has a stale copy,
and there is no way to tell which. So the whole family dies and both parties
must re-authenticate. Standard OAuth refresh-token-rotation behaviour (A07).

### Why logout doesn't revoke the access token

Sessions live in `refresh_tokens`; logout marks `revoked_at`. The access token
is deliberately left alive for its remaining ≤15 minutes.

A denylist would mean a store lookup on *every authenticated request* forever,
to close a 15-minute window. The cost/benefit does not favour it at this scale.
Worth knowing it is a conscious trade, not an omission.

## 9. API design

### Versioning belongs to the controller

```ts
@Controller({ path: 'auth', version: '1' })
```

Never `@Controller('auth')` bare. With `setGlobalPrefix('api')` and URI
versioning, routes resolve to `/api/v1/auth/login`.

The reason `API_PREFIX` and `API_DEFAULT_VERSION` are separate env vars rather
than one `api/v1` string: a breaking change ships as a **new controller**
(`version: '2'`) registered beside the old one. v1 keeps serving existing
clients, nothing global changes, and both versions live in the codebase
simultaneously. A controller can also serve both with `version: ['1', '2']`.

The health check is the deliberate exception — `VERSION_NEUTRAL` puts it at
`/api/health` so load balancer probes never need updating.

### One response envelope

```json
{ "data": {...}, "message": "Login successful", "status": 200 }
```

Applied globally by `ResponseInterceptor`; the per-route text comes from
`@ResponseMessage('...')` metadata. Errors get the same shape from
`AllExceptionsFilter`, plus `errors`, `timestamp`, and `path`.

The client parses one structure for every response, success or failure.

### Request/response naming asymmetry

**External JSON is `snake_case`. Internal TypeScript is `camelCase`.**

- `RegisterDto` has `first_name`, `phone_number`, `password_confirmation`.
- `User` entity has `firstName`, `phoneNumber`.
- Database columns are `snake_case` via explicit `@Column({ name: '...' })`.

The mapping is explicit at both boundaries: Zod schemas on the way in,
`toUserResponse()` on the way out. Slightly more typing, but renaming an entity
field cannot silently break the API contract.

### Response DTOs are allowlists, not entities

```ts
export function toUserResponse(user: User): UserResponseDto {
  return { id: user.id, first_name: user.firstName, /* ... */ };
}
```

Never return an entity directly. A new column — an internal flag, a moderation
note — stays private until someone adds it here **on purpose**. Serialising the
entity would leak it by default.

Belt and braces with `@Column({ select: false })` on `passwordHash`, so the hash
does not even load unless a query asks for it explicitly.

### Errors never leak internals

`AllExceptionsFilter` normalises everything:

- `QueryFailedError` → flat `"A database error occurred"`. Driver messages echo
  SQL and column names.
- Unknown exceptions → flat 500 `"Internal server error"`.
- `toMessage()` discards anything that is not a string or string array rather
  than coercing it — stringifying an arbitrary object risks spilling internals.
- Stack traces are logged server-side, never serialised (A05/A09).

There is also a subtle case handled: body-parser rejects oversized payloads
*before* Nest sees the request, and its errors carry a `type` tag instead of
being `HttpException`s. Without the explicit check they would surface as 500s.
The returned message is ours, so the configured limit is not disclosed.

### Uniform responses defeat enumeration

The API is designed so an attacker cannot learn which emails are registered
(A07). Five separate mechanisms:

| Endpoint | Technique |
|---|---|
| `login` | bcrypt compare against `DUMMY_HASH` when the email is unknown, so timing matches |
| `register` | 409 never says *which* field collided |
| `forgot-password` | identical message always |
| `verify-otp` | one message for wrong / expired / nonexistent |
| `otp.issue` | returns silently when rate-capped, so the response is unchanged |

`DUMMY_HASH` must stay a real cost-12 hash. A malformed string would fail fast
and reintroduce exactly the timing difference it exists to remove.

### Two independent rate limits

- **`@Throttle`** on the controller — keyed by IP **and email**
  (`ThrottleGuard.getTracker`), so rotating IPs does not let an attacker spray
  one account.
- **`MAX_ISSUES_PER_HOUR`** in `OtpService` — a database-backed per-address cap,
  independent of the request source entirely.

Two layers because the first is defeated by a botnet and the second is not.

## 10. House style

Conventions visible throughout, worth matching in new code.

**Comments explain *why*, never *what*.** Compare:

```ts
// Cap request bodies — auth payloads are tiny, so anything larger is abuse.
```

against the `// increment counter` style. Every non-obvious decision carries its
rationale, and security-relevant ones cite the OWASP category. That is what
makes a decision reviewable later rather than mysterious.

**No barrel files.** Every import names its file directly. Barrels (`index.ts`
re-exports) create circular-import hazards and hide the real dependency graph.

**`import type` for type-only imports.** With `module: nodenext`, this keeps
runtime imports and type imports distinct.

**Constants over magic values.** `OTP_LENGTH`, `BCRYPT_ROUNDS`,
`PG_UNIQUE_VIOLATION`, `REQUEST_TIMEOUT_MS`. Note `REQUEST_TIMEOUT_MS` is a
module constant rather than a constructor argument specifically because
`APP_INTERCEPTOR` resolves through DI and a bare `number` has no injectable
token.

**Config factories are typed and single-concern.** One `registerAs` per file,
each exporting its own interface. Security-sensitive settings (`jwt`, `cors`,
`mail`) get their own files so they can be audited in isolation.

**Fail fast at boot.** `env.validation.ts` throws on a missing secret rather
than defaulting. `durationToSeconds` throws on an unparseable duration rather
than silently minting wrong-lifetime tokens. A typo becomes a startup crash, not
a production mystery.

## 11. Toolchain gotchas

- **TypeScript is deliberately loose.** Only `strictNullChecks` is on;
  `noImplicitAny` and `strictBindCallApply` are off. Do not assume strict-mode
  diagnostics will catch mistakes.
- **Lint is type-aware** (`recommendedTypeChecked`), so errors can come from
  type information, not just syntax.
- **Prettier violations are ESLint errors.** Formatting breaks `npm run lint`.
  Run `npx eslint --fix` before committing.
- **`module: nodenext` but ESLint `sourceType: commonjs`.** Nest compiles to
  CommonJS — no top-level `await`, no `import.meta`.
- **`emitDecoratorMetadata` + `reflect-metadata` are load-bearing.** See §2.
- **`select: false` and explicit `select` interact.** When
  `findByEmailWithPassword` passes an explicit `select` list, *only* those
  columns load. Add a column to the entity and you must add it there too or it
  comes back `undefined` — with `strictNullChecks` not catching it, since the
  entity type says it is present.

## 12. Adding a feature — the checklist

Copy `api/v1/users/` (smallest complete example; `api/v1/auth/` is the
fullest).

```
modules/<feature>/
├── dto/            create-<feature>.dto.ts + update (partial of create)
├── entities/       <feature>.entity.ts — extends BaseEntity
├── repositories/   <feature>.repository.ts — wraps the ORM repo
├── <feature>.controller.ts
├── <feature>.service.ts
└── <feature>.module.ts
```

1. Entity extends `BaseEntity` (uuid `id`, `createdAt`, `updatedAt`), explicit
   `@Column({ name: 'snake_case' })`.
2. `npm run migration:generate -- src/database/migrations/<Name>` — then
   **read the generated file**; it is a schema differ, not a migration author.
3. Zod schema in `dto/`, type via `z.infer`.
4. Repository injecting `Repository<T>` via `@InjectRepository`.
5. Service with the business logic. No SQL.
6. Controller — `@Controller({ path: '...', version: '1' })`, never bare. Add
   `@ResponseMessage()` per route.
7. Module: `TypeOrmModule.forFeature([Entity])` in imports, export only what
   other modules genuinely need.
8. One line in `AppModule.imports`.

Do **not** add: response shaping, input sanitising, error formatting, or auth
checks. Those are `common/`'s job and already run.

### Tests

Two Jest configs, and the suffix decides the runner:

- `*.spec.ts` beside the code → unit runner (`rootDir: src`).
- `*.e2e-spec.ts` in `test/` → e2e runner (`test/jest-e2e.json`).

A `.spec.ts` placed under `test/` is picked up by **neither**.

## 13. What is deliberately not here

Knowing the gaps matters as much as knowing the design.

- **No queue.** Mail sends inline on the request path
  (`OtpService.issue` awaits `sendOtpEmail`). Laravel's `queue:work` has no
  counterpart running. Revisit with BullMQ when latency hurts or retries are
  needed.
- **No scheduled jobs.** `otp_codes` rows are marked consumed but never
  deleted, so the table grows without bound. `RefreshTokenRepository` already
  has `deleteExpiredBefore()` written but nothing calls it. Both want
  `@nestjs/schedule`.
- **No Swagger.** The feature-module pattern mentions Swagger decorators but
  `@nestjs/swagger` is not installed.
- **No cache / storage / logger modules.** Listed as planned in `shared/`.
- **No blog-post domain model yet** — the whole point of the project. Auth and
  users are the foundation.
